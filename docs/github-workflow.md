## 4. 작업 관리 방식

**이슈와 라벨**

개발 작업은 기능 단위 GitHub Issue로 등록하고 마일스톤에 배정합니다. 라벨은 계획서의 범위 구분을 그대로 사용합니다.

| 라벨 | 의미 | 이슈 예시 |
| --- | --- | --- |
| `필수` | 핵심 흐름 (촬영 → 요약 → 대조 → 저장) | ML Kit 한국어 글자 인식, 날짜·금액 대조 |
| `추가` | 편의 기능 | 달력 등록·전화·공유 버튼, 큰 글씨 모드 |
| `향후` | 학기 이후 확장 | 가상 독자 검수, 외국어 모드 |
| `bug` | 오류 수정 | 특정 안내문에서 마감일 추출 실패 |

1:1 미팅과 진행 미팅에서 받은 피드백도 이슈로 등록해, 다음 보고 때 반영 여부를 확인할 수 있게 합니다.

**커밋**

- 1인 프로젝트이므로 `main` 브랜치 하나로 운영합니다.
- 기능 하나가 동작하는 단위로 커밋해, 커밋 기록으로 개발 과정을 확인할 수 있게 합니다.
- 커밋 메시지는 한국어로 변경 내용을 한 줄로 쓰고, 관련 이슈 번호를 붙입니다. 예: `촬영 안내 화면과 가이드 틀 추가 (#1)`

**저장소에 올리지 않는 파일**

| 파일 | 이유 |
| --- | --- |
| `local.properties` | Gemini API 키 보관 |
| `google-services.json` | Firebase 프로젝트 설정 |
| `*.jks`, `*.keystore` | APK 서명 키 |
| 실제 안내문 원본 사진 | 이름, 주소 등 개인정보 포함. 문서에는 개인정보를 가린 사진만 사용 |

위 파일은 `.gitignore`로 제외합니다.

## 5. 진행 보고 방식

각 진행 미팅 전에 다음 두 가지를 준비합니다.

1. **진행 보고서** (`docs/progress/meeting-N.md`): 완료한 기능과 관련 이슈, 동작 화면 캡처, 계획 대비 변경 사항과 이유, 다음 미팅까지의 계획, 질문 사항
2. **GitHub Release**: 미팅 시점의 코드를 태그로 고정하고 시연용 APK를 첨부합니다.

| 시점 | 태그 | 내용 |
| --- | --- | --- |
| Progress meeting #1 | `v0.1` | 촬영 → 세 줄 요약 흐름 |
| Progress meeting #2 | `v0.2` | 필수 범위 완성 |
| Final Report | `v1.0` | 최종 버전 |

태그 사이의 변경 내역은 GitHub 비교 화면(`v0.1...v0.2`)에서 확인할 수 있습니다.
